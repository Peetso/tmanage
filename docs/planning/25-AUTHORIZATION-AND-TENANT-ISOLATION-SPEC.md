# TManage — Authorization and MySQL Tenant-Isolation Specification

## 1. Decision model

Authorization uses capability-based RBAC plus relationships and attributes. Inputs: principal, active membership, organization, internal/client role, workspace/project membership, action, object type/ID, audience, client-organization relation, direct assignment/share, sensitivity, and organization policy. The result is allow/deny plus field projection and audit requirement. Default is deny.

MySQL/MariaDB does not provide PostgreSQL-style row-level security. TManage therefore treats tenant scoping as a mandatory application invariant reinforced by database structure, least-privilege database users, composite tenant foreign keys, safe client projections, code-generation conventions, and adversarial isolation tests. UI hiding is never security.

## 2. Trusted request context

Authentication resolves a server-side session. The organization slug/ID from the route is accepted only after the API confirms an active internal or client membership. The API creates an immutable `TenantContext` containing `organizationId`, `userId`, `principalKind`, `membershipId`, capabilities, policy version, and correlation ID.

- Never accept trusted tenant or role values from arbitrary headers, request bodies, query strings, background-job payload content, or browser storage.
- Controllers cannot call the database directly. They call application services with a verified `TenantContext`.
- Tenant-owned repositories do not expose unscoped `findById`, `update`, `delete`, or free-form query methods. Their signatures require `TenantContext` or an explicit `organizationId` supplied only by a trusted service.
- Background and cross-tenant operations use separate, named service entry points, minimal database privileges, a reason code, and mandatory audit events.

## 3. Application policy sequence

1. Authenticate the current session and validate revocation/cutoff.
2. Resolve the requested organization against an active internal or client membership.
3. Build immutable trusted `TenantContext`; reject mismatch before object lookup where possible.
4. Load minimal policy facts using a query that includes the verified `organization_id`.
5. Evaluate capability, project relation, client relation, audience, and object state.
6. Select an explicit internal or client DTO/projection.
7. Execute the command in a transaction with optimistic version and domain invariants.
8. Record audit classification and outbox event in the same transaction.

## 4. Capabilities

`org.manage`, `org.security.manage`, `workspace.manage`, `project.create`, `project.manage`, `project.member.manage`, `conversation.read/write/moderate`, `work.read/create/update/transition`, `client_request.submit/triage`, `deliverable.create/review/publish`, `approval.read/decide`, `client_member.manage`, `audit.read/export`, `member.offboard`, `file.upload/download`, `search.use`.

Role-to-capability defaults come from `12-PERMISSION-MATRIX.md`; organization policy may narrow access and may never silently widen external access.

## 5. MySQL schema invariants

Every tenant-owned table has `organization_id CHAR(36) NOT NULL`. UUIDv7 values are generated by the application and stored in canonical lowercase text for Hostinger MySQL/MariaDB compatibility. A later binary-UUID optimization requires an ADR and measured evidence.

For each tenant-owned parent table:

```sql
ALTER TABLE projects
  ADD UNIQUE KEY uq_projects_org_id (organization_id, id);

ALTER TABLE work_items
  ADD CONSTRAINT fk_work_items_project_tenant
  FOREIGN KEY (organization_id, project_id)
  REFERENCES projects (organization_id, id);
```

Rules:

- Every tenant-owned child-to-parent relationship uses a composite foreign key containing `organization_id`; a globally unique ID alone is insufficient.
- Every lookup, update, delete, join, cursor, uniqueness rule, and lock on tenant data begins with or includes `organization_id`.
- Updates cannot change `organization_id`; moving data between organizations is an explicit audited migration workflow.
- MySQL `JSON` is allowed for structured content and metadata, but ownership, permissions, state, relations, money, deadlines, and searchable filter fields remain typed columns with constraints/indexes.
- Use strict SQL mode, `utf8mb4`, UTC connections, `DATETIME(3)`, InnoDB, foreign keys, parameterized queries, and explicit transactions.
- Separate migration and runtime database users. The runtime user has only the DML privileges the application needs and cannot alter schema, grant privileges, create users, or access other databases.

## 6. Repository and query guardrails

Use Drizzle ORM with the `mysql2` driver, schema-owned repositories, and explicit SQL migrations. ORM convenience never overrides tenant boundaries.

Required patterns:

```ts
async function getWorkItem(ctx: TenantContext, id: string) {
  return db.query.workItems.findFirst({
    where: and(eq(workItems.organizationId, ctx.organizationId), eq(workItems.id, id)),
  });
}
```

- Ban direct `db` imports outside repository/migration modules with lint boundaries.
- Ban raw SQL except reviewed, parameterized helpers in an allowlisted directory.
- Mutation repositories derive `organization_id` from `TenantContext`, never from the DTO.
- Use an organization-bound transaction wrapper and require it for multi-write commands.
- Development/test query instrumentation rejects access to tenant tables when a tenant predicate is missing; CI combines this with the isolation corpus below.
- Code review is mandatory for repositories, migrations, authorization policies, client projections, exports, search, and admin/service paths.

## 7. Client-safe projection pattern

Internal DTOs are still capability-filtered. Client DTOs are selected from dedicated client-projection tables or explicit allowlisted queries; forbidden fields are never fetched into the client response path. Forbidden client fields include internal notes, private comments/messages, estimates/cost/margin, staff evaluation, internal risk rationale, security metadata, other-client identities, hidden custom fields, unreleased versions, and internal file keys.

Client reads must match all of: service `organization_id`, active client membership, matching `client_organization_id`, project/client relation, client-visible audience, and published/version state. Clients never write projection JSON directly; publishing is an internal capability that transactionally creates an immutable client-safe version.

Never implement client access as `serializeInternalObject(); delete fields`.

## 8. Approval decision policy

Allow only when: organization matches; active client/internal relationship exists; approval is requested/viewed; reviewer assignment belongs to the current user; due/expiry policy permits; content hash equals the governed version; reviewer has not issued a terminal current decision; and organization policy allows the method. The transaction locks approval/reviewer rows, rechecks organization/hash/state, writes the append-only decision, updates the aggregate, audit, outbox, and idempotency result.

## 9. Storage, cache, search, and realtime authorization

- Object key: opaque organization namespace/project/object/version. Users never construct a key.
- Download: API authorizes current access then issues a URL valid for at most five minutes; external highly sensitive download may use a one-time proxy.
- Cache: key starts with organization and policy version; internal/client DTOs never share a cache key.
- Search: materialized documents carry organization, project, audience, client organization, and authorization attributes; the MySQL query starts with organization scope and final authorization runs before returning snippets/results.
- Realtime: subscriptions are authorized at join; sensitive events are rechecked before broadcast; membership suspension disconnects sockets.

## 10. Background jobs and admin paths

Job payloads contain event ID, organization, actor/effective actor where relevant, object reference, and policy version—not raw content. Workers resolve the organization and object again using scoped repositories. User-facing actions/notifications recheck current authorization to prevent delayed leaks.

Cross-tenant owner support, data repair, export, and migration tools are separate commands with step-up authentication, allowlisted actions, dry-run preview, reason/ticket, bounded target organizations, rate limits, and immutable audit. The normal web/API runtime never receives an unrestricted cross-tenant repository.

## 11. Permission and isolation test grid

Every operation is tested for: correct internal project; same organization/different project; same organization/different client; different organization; suspended membership; expired client membership; direct-ID enumeration; changed role after session; archived/deleted object; stale cache/search; delayed job; realtime subscription before revocation; object moved/reshared.

The CI isolation corpus seeds two organizations with intentionally similar IDs/names and verifies reads, writes, joins, bulk changes, exports, search, notifications, websockets, files, jobs, and admin paths. Tests inspect both HTTP outcomes and database side effects. A missing `organization_id` predicate, cross-organization composite-FK failure, or leaked field fails the release.

## 12. Audit-required decisions

Role changes, invitations, external publish, approval decision/invalidation, restricted export download, client membership change, policy change, offboarding, export, API/webhook credentials, admin impersonation, cross-tenant support action, and any emergency database procedure require audit. Denied sensitive attempts are security events with safe metadata.
