# Performance run, 2026-10-25

First real run of `scripts/load/run.mjs` against a live local stack. Measured, not fixed: every
miss below is listed with the route and the query behind it, for a later slice.

## Set-up

- Database: a private MariaDB 11.8.9 (`scripts/db/mariadb-server.mjs`, the production engine),
  real migrations, the two-tenant seed, then grown through the API to **10,003 work items** in
  one Northstar project (PERF-02's 10k) and **2,000 messages** in one channel.
- API (`tsx src/main.ts`, development mode for the dev sign-in route) with the production pool
  size (`DATABASE_POOL_MAX=5`). The general rate limit was raised for the run, because 300
  requests a minute per user would answer 429 within a second; latency is under test, not the
  limiter.
- Worker in loop mode with the realtime socket on (`REALTIME_PORT`), the API serving its
  `ws://localhost` URL.
- Load: 10 concurrent loops, 3 signed-in users (owner, manager, designer), 2 s warm-up and
  20 s measured per route; the fan-out probe used 50 subscribed sockets and 20 messages 1.5 s
  apart. One Windows laptop runs client, API, worker and database together, so absolute numbers
  are pessimistic; the pass/miss picture repeated across three runs.
- Command: `node scripts/load/run.mjs --world world.json --fill-work 10000 --fill-messages 2000`
  for the fill, then `--realtime-sockets 50` for the measured run (see `scripts/load/README.md`).

## Misses

1. **Home My Day (PERF-01, NFR-04).** `GET .../home/my-day` runs
   `MyDayRepository.listOwnedOpen` (`apps/api/src/modules/home/my-day.repository.ts`): every
   open item the user owns, all columns including `description`, no `LIMIT`, ranked in
   JavaScript and returned whole. With ~3,300 open items per user the slow log shows that
   statement at 162-178 ms average, 351 ms worst, ~13,000-14,000 rows examined per call (the
   `ix_work_items_org_owner_state_due` index is used, then a filesort on `due_at, id` over the
   `IN (states)` range); the rest is serialising thousands of rows per response. The route
   needs a bounded read (a cap or page per reason, only the columns the card shows).
2. **Realtime fan-out (NFR-06, PERF-06).** Delivery waits for the worker's outbox poll:
   `OUTBOX_POLL_INTERVAL_MS` defaults to 5,000 ms (`packages/config/src/env.ts`,
   `.env.example`), so a frame lands on average half a poll late (p50 2.2 s, p95 4.5 s). The
   socket fan-out itself is fast: with a 250 ms poll the same 50 sockets saw p95 251 ms and no
   lost frames. The Hostinger app's in-process worker (`apps/server/server.mjs`) starts no
   socket server, so live clients rely on refetch, which the probe does not measure.

## Near misses and notes

- **Search (PERF-03)** passes, but `search-index.repository.ts` filters with
  `title LIKE '%term%'`, a full scan of the tenant's work items (10,002 rows examined, 76 ms
  average, 739 slow-log hits in 15 s). It will cross 500 ms as the corpus grows past 10k.
- **Work list (PERF-02)** passes with 10k project items; p95 varied 63-278 ms with machine load.
- **Log volume:** every authenticated request writes two or three `[tenant-guard]` lines
  (~1 KB each, the allowed membership-resolution reads, `apps/api/src/app-composition.ts`);
  run 2 wrote 61 MB of API log in about three minutes.
- **NFR-05 (portal LCP < 2.5 s, PERF-05)** is a browser measurement of the web app and is not
  covered by this API load test; it is not measured here.
